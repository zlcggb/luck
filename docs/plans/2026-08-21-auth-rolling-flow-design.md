# 管理账号认证与轮动签到抽奖闭环设计

## 目标

活动管理者从首页选择转盘式或轮动式后，必须注册并登录才能创建项目、配置签到和进入管理抽奖页。参会者继续通过活动专属链接公开签到，不要求管理账号。注册不验证邮箱，成功后返回登录表单；登录完成后恢复用户选择的抽奖模式。

## 路由与认证

- 公开：`/`、`/login`、`/checkin`、`/lottery/employee`、`/lottery/personal-wheel`、携带活动 ID 的转盘参与页。
- 受保护：`/projects`、`/project/:projectId`、`/lottery`、`/lottery/rolling`、`/lottery/wheel/admin`、`/display`。
- 首页两种模式统一进入 `/projects?create=<mode>`。未登录由路由门禁重定向到 `/login?next=...&mode=...`，登录成功再恢复目标。
- `next` 只接受站内绝对路径，防止开放重定向。

## 注册与视觉

登录/注册使用同一卡片切换。注册包含姓名、邮箱、密码、确认密码；成功后即使 Supabase 返回 session 也主动登出，显示“注册成功，请使用新账号登录”，保留邮箱并清空密码。Supabase 项目关闭 Confirm Email。

视觉采用浅色 macOS 控制台：四级语义灰、单一系统蓝、磨砂玻璃面板、细边框与柔和阴影。动画只用于卡片入场和状态切换，并尊重 `prefers-reduced-motion`。

## 轮动签到与抽奖数据流

签到调用单一数据库函数：校验活动状态、标准化工号、upsert `luck_participants(status='checked_in')`、写入唯一签到记录并关联 `participant_id`。整个函数在一个事务内完成，重复请求返回现有签到。

轮动管理页只加载 `checked_in` 参与者，数据库返回空数组时显示空状态，不能回退 localStorage 或模拟数据。Realtime 用于更新展示；每次正式抽奖前重新读取数据库。中奖写入和奖项余量扣减由数据库函数原子完成。

## 安全与失败处理

- 匿名角色只能读取公开活动必要字段并执行签到函数，不得修改项目、奖项或中奖数据。
- 管理数据按 `luck_events.owner_id -> luck_users.auth_id -> auth.uid()` 授权。
- 重复签到、关闭中的活动、奖项余量不足和重复中奖返回稳定错误码。
- Realtime 断线不影响正确性，开奖前的数据库刷新是最终准入检查。

## 验收

- 未登录直接访问轮动管理 URL 会进入登录页，登录后恢复原目标。
- 两种首页模式都要求管理账号，登录后自动打开对应项目创建模式。
- 注册后不出现查收邮件提示，可立即用新账号登录。
- 同一活动同一工号并发签到只产生一个参与者和一条签到记录。
- 真实抽奖池为空时绝不展示模拟参与者；新签到可实时进入池。
- 匿名用户不能更新项目/奖项或写中奖记录。
